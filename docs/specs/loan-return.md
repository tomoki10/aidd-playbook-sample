# spec: 備品の返却（記入例）

- 元の intent: [docs/intents/loan-return.md](../intents/loan-return.md)（総務部）。状態: 受け入れ済み
- 適用した Skill: secure-api

## 要件

- R1. 借り手本人は、自分の貸出を返却できる。返却すると、その備品はすぐに借りられる状態になる
- R2. 管理者（総務部）は、窓口で受け取った備品について、他人の貸出を代理で返却できる
- R3. 本人と管理者以外の利用者は、他人の貸出を返却できない。その貸出が存在するかどうかも分からない
- R4. 返却済みの貸出は、もう一度返却できない
- R5. 返却期限を過ぎた貸出も返却できる
- R6. 誰がいつ返却したか（拒否された試行を含む）を、後から監査ログで確かめられる。応答と監査ログに借り手の連絡先は出さない

## 設計

- 既存の貸出 API に、返却のエンドポイントを追加する。既存の認証（Bearer トークン）の後ろに置く
- 本人か管理者かの判定と、返却済みかの判定はドメイン関数に寄せ、ルートは結果を HTTP の応答に変換するだけにする
- 返却日は、サーバーの時計から求めた今日の日付にする。クライアントから日付を受け取らない
- 返却時の備品の状態は新しく持たない

## intent の制約をどう満たすか

| 制約 | 満たし方 |
|---|---|
| 他人の貸出を返却できてはいけない | R3。本人か管理者かの判定をドメイン関数で行う |
| 期限を過ぎていても返却は受け付ける | R5 |

## intent から持ち越した未解決の問い

- 返却時に備品の状態（破損など）を記録するか → 今回は扱わない。必要になったら別の intent にする

## 懸念点

1. 本人以外に「権限がない」と返すと、他人の貸出 ID が有効かどうかが分かってしまう。貸出が存在しない場合と同じ応答にする（R3）。担当: テックリード
2. 監査ログに借り手の連絡先が混ざると、ログを見られる人に個人情報が広がる。記録するのは操作した人、操作、対象の貸出 ID、結果だけにする（R6）。担当: エンジニア
