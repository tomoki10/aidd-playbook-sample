# 承認ゲートのセルフレビュー用チェックリスト

研修は個人ワークなので、承認も自分で行います。役を切り替えて、次の項目を確かめてから PR をマージします。実際のチームでは、括弧内の役の人が承認します。

## intent.md（PO）

- [ ] 問題が「誰が・どんな場面で・何に困っているか」で書かれている
- [ ] 期待する結果が、解決策ではなく「できるようになること」で書かれている
- [ ] 影響を受ける利用者とシステムが挙がっている
- [ ] 制約（権限、期限、やってはいけないこと）が書かれている
- [ ] 決めていないことが「未解決の問い」に残っている

## spec.md（PO、テックリード）

- [ ] 要件が R 番号付きで、利用者から見た振る舞いとして書かれている
- [ ] 設計が方針（どこに何を足すか、何を持たないか）に留まっている
- [ ] intent の制約ごとに満たし方が書かれている
- [ ] 未解決の問いの扱いが書かれている
- [ ] 懸念点に担当がある
- [ ] 適用した Skill が書かれている

## 分割計画（テックリード）

- [ ] spec へのリンクがある
- [ ] 並行に実装するタスクが、同じファイルを触らないように分かれている
- [ ] 「変更するファイル」に、境目の関数のシグネチャと戻り値の型、API の応答とエラー（ステータスと code）が書かれている
- [ ] 「作業順」に、スタブから各タスクのマージまでの順番が書かれている
- [ ] 「リスク」と「成功を示すテスト」が書かれている。テストが spec の要件（R 番号）に対応づいている

## plan.md（エンジニア）

- [ ] spec と Issue へのリンクがある（並行に実装するときは分割計画へのリンクも）
- [ ] 見出しが「変更するファイル／作業順／リスク／成功を示すテスト」になっている
- [ ] 「変更するファイル」に、触らないファイルも書かれている
- [ ] 分割計画で決めた境目の関数を変えていない
- [ ] 「成功を示すテスト」に、確かめ方（実行するコマンド）が書かれている

## 実装の PR（レビュアー）

- [ ] plan.md のコミットが実装のコミットより前にある
- [ ] `npm run lint && npm run typecheck && npm test` が通る
- [ ] spec の要件（R 番号）ごとにテストがある
- [ ] 差分が plan の「変更するファイル」に収まっている
