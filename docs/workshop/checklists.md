# 承認ゲートのセルフレビュー用チェックリスト

研修は個人ワークなので、承認も自分で行います。役を切り替えて、次の項目を確かめてから PR をマージします。実際のチームでは、括弧内の役の人が承認します。

## intent.md（PO）

- [ ] 問題が「誰が・どんな場面で・何に困っているか」で書かれている
- [ ] 期待する結果が、解決策ではなく「できるようになること」で書かれている
- [ ] 影響を受ける利用者とシステムが挙がっている
- [ ] 制約（権限、期限、やってはいけないこと）が書かれている
- [ ] 決めていないことが「未解決の問い」に残っている
- [ ] どう作るか（エンドポイントやデータ構造）を書いていない

## spec.md（PO、テックリード）

- [ ] 冒頭に元の intent、状態、適用した Skill が書かれている
- [ ] 要件が R 番号付きで、利用者から見た振る舞いとして書かれている
- [ ] 設計が方針（どこに何を足すか、何を持たないか）に留まっている。応答の項目、エラーのコード、関数のシグネチャを書いていない
- [ ] intent の制約ごとに満たし方が書かれている
- [ ] intent で解決しない問いが決まっている
- [ ] 懸念点に担当がある

## 実装 Issue（エンジニア、テックリード）

- [ ] spec と、この Issue で満たす要件（R 番号）が書かれている
- [ ] 範囲（触る・触らない）が書かれ、並行するほかの Issue と同じファイルを触らない。共有するファイルがあれば、どう扱うか（再生成など）が書かれている
- [ ] 互いの関数を呼ぶなら、境目の関数のシグネチャと戻り値の型が書かれている。呼ばないなら「なし」になっている
- [ ] API を足す・変えるなら、応答とエラーコード（ステータスと code）が書かれ、spec の要件（返さない情報、見せない相手）と食い違っていない
- [ ] マージの順番を決める必要があるなら、本文に書かれている
- [ ] 受入テストが spec の要件（R 番号）ごとに、観点（どんな状態で・誰が・何をするか）と期待値（結果、ステータス、code）で書かれている。テストコードは書いていない
- [ ] 境界値（例: 期限の当日と翌日、上限ちょうど）と、拒否する場合（例: 本人以外、存在しない、認証なし）が観点に入っている
- [ ] 観点と期待値に PO とエンジニアが合意してから、`ready-for-agent` を付けている

## plan.md（エンジニア）

- [ ] 見出しが Approach／Risks／Verification の3つで、それぞれ数行に収まっている
- [ ] Approach が、spec の要件をその作業でどう満たすかの言葉で書かれている。ファイル名、関数の中身、テストの一覧を書いていない
- [ ] Approach が Issue の範囲（触る・触らない）と境目の関数から外れていない
- [ ] Verification に、要件をどう確かめるかが書かれている
- [ ] 実装より先にコミットされている

## 実装の PR（レビュアー）

- [ ] PR 本文から Issue、intent、spec、plan へリンクしている
- [ ] plan.md のコミットが実装のコミットより前にある
- [ ] `npm run lint && npm run typecheck && npm test` が通る
- [ ] テストが実装と同じ PR に入っていて、テスト名に R 番号が付いている
- [ ] Issue の受入テストの観点と期待値が、すべてテストになっている。テストの期待値が Issue と食い違っていない
- [ ] コミット済みのテストを書き換えていない（`protect-tests.sh` で止まったら、テストではなく実装の側を直す）
- [ ] 差分が Issue の範囲に収まっている（`git diff --name-only main...HEAD`）。外れた箇所には理由がある
