# intent: エラー率の急増への対応（Maintain の診断例）

- 起票 Issue: #10（エラー率の異常（2026-10-05、z=3.5179）、`triage` ラベル）
- 起案者: 運用担当（maintain ワークフローの検知を受けて、ローカルの Claude Code が読み取り専用で診断）
- 状態: PO のトリアージ待ち

## 問題

2026-10-05 のエラー率（5xx 応答の割合）が 1.18% で、当日を除く直近28日の平均 0.972%、標準偏差 0.0591 に対して z=3.52 だった。`maintain/tiers.yml` の 3σ（提案）に当たる。

直近7日は 0.89〜1.01% で推移しており、前日までに上昇の兆候はない。1日だけの急増である。

同じ時期のリポジトリの変更を見ると、10-05 の直前に機能 B（`POST /loans/:id/extend`）がマージされ、production に模擬デプロイされている。延長 API は既存の貸出を書き換える初めての更新系 API で、`deps.loans.save` の呼び出し経路が増えた。ただし、メトリクスにはエンドポイント別の内訳がなく、延長 API が原因かどうかはこのデータだけでは判断できない。

## 期待する結果

- エラー率の急増の原因が、エンドポイント単位で特定できている
- 原因が延長 API なら、再発を防ぐテストが追加され、修正がマージされている
- 次に同じ規模の急増が起きたとき、エンドポイント別の内訳から原因の候補をすぐに絞れる

## 影響を受ける利用者とシステム

| 対象 | 影響 |
|---|---|
| 借り手（社員） | 貸出・返却・延長の操作が 1% 強の割合で失敗している可能性がある |
| 総務部（管理者） | 備品の空き状況や自分の貸出の参照が失敗すると、問い合わせが総務部に戻る可能性がある |
| 貸出 API 全体 | エラー率の上昇。どのエンドポイントかは未特定 |
| Maintain の仕組み | メトリクスがエンドポイント別に分かれておらず、診断の根拠が弱い |

## 制約

- 診断はメトリクスとリポジトリを読むだけで行った。本番の設定やデータは変更していない
- 原因が特定できるまで、延長 API を止める判断はしない（エラー率は 1.18% で、全体の利用は継続できている）
- 閾値（`maintain/tiers.yml`）を緩めて検知を消す対応はしない

## 未解決の問い

- 急増は延長 API のマージと関係があるか → エンドポイント別のエラー率を取れるようにしてから確かめる
- 翌日以降も高い値が続くか → 翌日の maintain の結果で判断する。平常に戻れば一過性として記録だけ残す
- メトリクスにエンドポイント別の内訳を追加するか → 追加するなら別の intent にする
